# Packaging Policy

## 1. 当前包的目标

当前包的目标不是还原一个可直接构建运行的完整仓库，而是形成一个适合：

- 理解系统
- 维护主逻辑
- 追踪核心能力
- 二次扩展逻辑包

的稳定分层逻辑包。

## 2. 当前采用的强制规则

### 必须整包进入

- `src/tools/`
- `src/Tool.ts`
- `src/tools.ts`
- `src/services/tools/`

### 必须保留关键外围系统

- `src/utils/permissions/`
- `src/services/mcp/`
- `src/skills/`

### 当前只保留索引与映射

- `src/state/`
- `src/context.ts`
- 大型 UI 组件目录

### 当前已提升为原始层保留

- `src/commands/`

## 2.1 对 Agent 的强制执行规则

- 本逻辑包不是静态文档，而是后续所有 Agent 的统一入场规则。
- 当任何 Agent 开始一个新项目、一个新模块、一个新子系统或一个新阶段时，必须先读取主逻辑并按主逻辑做接入判断和规划。
- 对新增模块场景，规划不是可选项，而是强制前置动作。
- 只有这样，逻辑包才能作为稳定基线降低错误率，而不是只作为归档材料存在。
- `AgentLogic_V6` 逻辑包只能作为外挂脑和规则包存在，不能被当作新项目目录、模块目录、依赖目录、构建目录或临时文件目录。
- 如果当前任务要创建项目文件，默认必须先确认或创建独立工作目录，再把 V6 作为外部逻辑基线接入。
- 在确认或创建独立工作目录之前，Agent 必须先完成目录审计，判断当前路径是否落在 V6 逻辑包范围内。
- 如果目录审计命中 V6 范围，则当前路径下禁止继续创建任何业务文件。

## 3. 为什么不直接整包复制整个仓库

- 那样会稀释逻辑包的阅读效率。
- 维护者会失去“什么最重要”的信号。
- 逻辑包的职责是“高密度理解 + 关键实现保留”，不是“源仓库备份”。

## 4. 未来升级建议

如果你要继续推向更完整版本，建议后续优先级如下：

1. 增加 `raw_context_state/`，保留 `context.ts` 与核心状态入口
2. 为 tools / permissions / mcp / skills / commands 建立更细的跨目录调用图
3. 补一份 feature flag 与 stub 的独立矩阵
4. 对 commands 建立“命令到工具/模块”的一览表

## 5. 第三方增强工具的纳入原则

像 `Magika` 这类第三方文件智能工具，默认不直接进入主逻辑强制层。

纳入判断建议如下：

- 如果只是能增强精度或体验，但当前主链路已经成立：
  - 记为 `candidate`
  - 写入能力矩阵或未来增强项
- 如果已经被仓库正式集成，并形成稳定调用链：
  - 再考虑提升为更高优先级能力
- 如果不引入它会导致当前系统主链路失真或无法成立：
  - 才考虑将其升级为主逻辑强制项

对当前项目而言，`Magika` 属于第一种情况：有增强价值，但不是当前 V6 的必需依赖。
